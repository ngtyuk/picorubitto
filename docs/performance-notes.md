# 性能メモ

現在のランタイムの性能特性と、ゲーム実装・計測に必要な設定をまとめます。
APIの引数と上限は[APIリファレンス](api-reference.md)、メモリと実行先の責務は
[ランタイム構成](runtime-architecture.md)、検証の入口は[互換性テスト](compatibility-testing.md)を
参照してください。

## 標準release設定

`ruby tools/build/workflow.rb engine`は次の構成を使います。

| 項目 | 既定値 |
| --- | --- |
| 出力 | 320×240、RGB565（1画面153600バイト） |
| カラー | SRAMのダブルフレームバッファ |
| TFT転送 | Core 1 presenter、SPI要求値75MHz、DMA |
| 更新範囲 | dirty rect、背景レイヤー、32行の転送ストライプ、結合余白256画素 |
| スプライトキャッシュ | SRAM 64KiB。収まらないデータはPSRAM |
| ゲームCコード | 速度最適化を有効化 |
| PicoRubyのVMコア | `--vm-opt size`（`-Os`） |
| 3D | 線クリップ、投影キャッシュ、低解像度深度SRAM、Model共有を有効化 |
| 三角形走査 | spans |
| 音声 | PWM、BGM 1音とSE最大4音。I2Sとダイヤルは明示的に有効化 |

パネルや配線で表示が不安定な場合は`--tft-clock 40`などで下げて確認します。
`Game.tick(60)`の60は目標FPSです。実測FPSは統合ROMかprofilingログで確認します。

## メモリ配置

Core 0のスタックはSRAMに16KiB、Core 1は4KiBを予約します。VMヒープはPSRAMの先頭4MiBを
使い、残りへ起動バッファ・ROM・アセット用ヒープを配置します。
アセットの保持量は`Game::Assets.resident_bytes`で確認できますが、VMや全SRAMの空き量では
ありません。ブラウザでも、仮想SDの元データやブラウザ内部の管理領域を含みません。

Core 1 presenter構成では、3Dの内部画素数が19200以下の場合に固定38400バイトのSRAM深度領域を
使います。大きい解像度には153600バイトのPSRAM領域を使います。解像度変更では追加確保せず、
次の`ThreeD.begin_frame`で使用範囲をクリアします。深度作業領域はアセット保持量に含みません。

## 2D描画とアセット

- 静的背景は登録し、動くものの描画前に`Display.begin_frame`で必要な領域を復元します。
- 毎フレーム全面を消去・描画すると、dirty rectの転送量削減が小さくなります。
- スプライトは`draw_batch`で境界呼び出しをまとめます。
- 画像・フォント・音声は事前にロードし、ループ中のSDアクセスや繰り返し確保を減らします。
- シーン終了時は不要な参照を外し、必要なら`Assets.collect`を呼びます。背景の参照も解除します。

dirty rectは、結合後の面積が個別転送と余白の許容量を超える場合に別々に送ります。
64矩形を超える場合は全面転送へ戻ります。
テクスチャは最近傍で拡大縮小します。拡大率やクリップ範囲で描画量が変わるため、
等倍・拡大・縮小を対象ゲームで比較してください。

組み込み漢字は6,355字を実機のフラッシュ上に約161KiBの固定データとして保持し、
描画時に二分探索します。ブラウザでは同じデータを起動時に約161KiBのバイト配列へ
展開します。これはゲームのアセット保持量には含まれません。

PBFはロード時に全体を検証し、描画時は可視の文字範囲を走査します。
WASMの文字キャッシュは全フォント合計256件・予算1MiBで、画像または描画区間を再利用します。
大きすぎる文字は可視画素を直接描き、Fontの回収や明示回収でキャッシュを破棄します。

## 3D描画

`Game::ThreeD`は低ポリゴン向けのソフトウェアラスタライザです。通常の座標範囲では
固定小数点の変換・投影・走査を使い、対応範囲外では浮動小数点経路へ戻ります。

`ThreeD::Model`を使うと、形状を登録してインスタンス変換だけを渡せます。
実機は保持した作業領域で頂点を変換し、WASMも形状を保持します。
WASMの変換JSONとレンダラ内の一時オブジェクトは描画時に生成されます。
Modelの面と線は同じインスタンス内でカメラ変換と投影を共有します。

- 内部解像度160×120は320×240に対し、深度クリアと内部画素数が4分の1です。
- `set_viewport`で320×240へ最近傍拡大できます。ちょうど2倍の場合は専用経路を使います。
- 共有頂点の形状は`Model`または`draw_indexed_mesh`を使い、頂点変換の重複を減らします。
- 線は共有辺を重複なく指定し、必要な場合だけ深度判定なしで重ねます。
- 3Dをまとめて描いた後に2D HUDを描くと、ブラウザのCanvas取得・反映をまとめられます。
- 大面積の三角形や重なりを増やすと画素走査が増えます。nearを必要以上に小さくしないでください。

三角形のspans走査は行の有効区間を走査し、幅16画素未満ならrowsへ戻ります。
範囲外の固定座標等では従来経路へ戻ります。

カメラ変換や投影の処理回数をホストで調べるには、
`python3 tools/diagnostics/model_work.py`を使います。`--no-model-shared`で共有なしの
処理回数と比較できます。処理回数は実機の時間測定とは区別します。

## 画面転送

標準のCore 1 presenterでは、Core 0がゲーム更新・描画を行い、Core 1がTFT SPI0・DMAと
転送ストライプを所有します。Core 1はPSRAMへ直接アクセスしません。
SRAM framebuffer、dirty rect、背景レイヤーを使います。

## 音声と保存

BGMは最大1 MiBをPSRAMへ全読み込みします。長いWAVほど画像などの空きを減らし、
SDからの読み込みも長くなります。ループ再生では音源の先頭と末尾の波形を整えてください。

PWMの音声DMA完了時は、準備済みの次バッファを開始してから空きバッファを補充します。
I2Sは2つのDMAをチェーンし、次の転送開始を割り込み待ちから切り離します。
PWMは2048サンプル×2、I2Sは512ステレオフレーム×2で、各4096バイトです。
I2Sは48kHz・16-bitで、入力WAVの合成と線形リサンプリングも割り込み内で行います。
補間の積と除算は32-bitへ収まるように符号を分離し、64-bit除算ヘルパーへの依存を除いています。
音声の固定ゲインはBGM 1/2、SE各1/8です。API 15以前と音量は異なります。
最初の4096サンプルだけPCMのFNV-1aと最大隣接差を計測し、その後のハッシュ更新は省きます。
I2Sの補充期限は約10.67msです。各バッファは2048バイト境界に揃えるので、リンカの配置によって
SRAMにパディングが追加されます。
停止時／次の再生前の`AUDIO: I2S stats`で、`stalls`（再生中に観測したFIFO空によるPIO停止）、
`late_irqs`（再読込中のバッファを検出）、`late_refills`（補充が10666µs以上）、
`refill_max_us`（最大補充時間）を確認します。割り込みでログ出力は行いません。
最終バッファの再生中に新しい音が追加された場合は、停止済みDMAを補充後に再開します。
この境界では短い無音やPIO停止が生じる可能性があり、実機での聴取が必要です。
ゲームのフレーム更新中はDMA完了数も監視します。再生中に250ms以上進行がなければ、
Core 0からI2SとDMAを停止して再開し、`AUDIO: I2S watchdog`を出力します。ループBGMが
あれば先頭から再開し、なければ再生中のSEを1つ再開します。ほかの重なったSEは停止します。
この復旧はDMA割り込みが進まない場合に限り、配線やアンプ側の無音は検出できません。
表示・SDアクセスとの併用、実機の音の連続性・聴取は別に確認します。

WeActのI2S実機確認（2026-10-27）では、STATIC／DRAWは正常に再生され、LIVEだけに
断続音が発生しました。モードを繰り返し切り替えても同じ傾向で、DINのGP17→GP28移設や
表示後200ms待つ診断ROMでは改善しませんでした。TFTの40MHz指定も改善策にはならず、
比較時にはDRAW／STATICでも悪化しました。
アンプのGNDからWeActの空きGND端子へ配線を追加すると、LIVEでも断続音が聞こえなくなった
との実機報告があり、この構成で残っていたノイズはGND経路の影響が主因と判断しています。
これはPCMの符号演算修正後に残っていたノイズの確認結果です。電気波形の測定は行っていません。
配線上の注意は[実機ガイド](hardware.md#max98357aのi2s出力)を参照してください。

音量ダイヤルは50Hzで4回平均し、平滑化します。ADC値128以下が無音、3800以上が最大音量です。
音量の反映には平滑化と既存DMAバッファの待ちが加わります。
`--audio-max-gain`はダイヤル適用後に固定ゲインを掛けます。100%は従来と同じPCMで、
50%は振幅を半分にします。実機での処理時間・音質は対象ボードで確認してください。
セーブは最大32KiBの同期書き込みなので、毎フレームの保存は避けます。
音声出力とダイヤルの設定・配線は[実機ガイド](hardware.md)を参照してください。

## 計測する

通常のrelease設定へprofilingを追加し、別ディレクトリへ出力できます。

```sh
ruby tools/build/workflow.rb engine --profiling \
  --firmware-dir build/firmware-profile
ruby tools/build/workflow.rb checks
```

| ログ | 意味 |
| --- | --- |
| `fps` / `frame_us` | 実測FPSとフレーム全体の時間 |
| `present_us` | Core 0の表示API呼び出し時間 |
| `present_core1_wait_us` | Core 1構成の空きバッファ待ち |
| `present_core1_submits` / `present_core1_stalls` | フレーム提出回数と所有権待ちの発生回数 |
| `present_copy_us` / `present_window_us` | Core 0転送構成でのコピー・ウィンドウ設定時間 |
| `present_dma_wait_us` / `present_spi_idle_us` | Core 0転送構成でのDMA・SPI待ち |
| `present_dma_submits` / `present_pipeline_stalls` | DMA提出回数とストライプ準備の遅れ |
| `sprite_us` / `clear_us` / `dirty_bytes` | スプライト・消去時間、転送画素バイト量 |
| `other_us` | Ruby処理、境界呼び出し、未分類処理など |

Core 1構成の`present_us`は物理転送そのものの時間ではありません。並行する処理の内訳も
単純合計せず、`frame_us`と実測FPSを合わせて判断します。
統合ROMのPERF項目は暖機後に固定負荷を繰り返し、更新・描画・表示の時間を記録します。
ボード、ソースのコミット、ROM識別値、ビルド設定、解像度を揃えて比較してください。

VMコアの比較には`--vm-opt size|speed`を使います。speedは`picoruby-mruby`だけを`-O2`へ
切り替え、描画C・WASM・ホストコンパイラの最適化は変更しません。
処理によって効果が異なるため、標準はsizeです。

ホストの実行時間やブラウザのFPSは、RP2350の速度・PSRAM帯域・TFT転送を表しません。
ゲームの性能判断では実機の表示・入力・音声と連続稼働を確認します。
