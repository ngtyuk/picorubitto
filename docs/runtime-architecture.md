# ランタイム構成

ゲームのRubyコードと`Game` APIを共有し、ハードウェアに依存する処理だけを実行先ごとに
実装します。

```text
ゲームRuby / game.mrb
        │
        │ Game API
        ▼
共通ビルド設定
   ┌────┴────┐
 RP2350     WASM
 C / SPI    Ruby adapter / JavaScript
 DMA / SD   Canvas / 仮想SD
 PSRAM      Web Audio / ブラウザ保存
```

依存バージョンとROM形式は[依存バージョン](dependencies.md)で管理します。PicoRuby 4.0.5の
mruby構成を実機・WASM・ホスト/ブラウザコンパイラで揃えます。

## RP2350のVM最適化プロファイル

TFT初期化後、SD／ROMに依存しない起動画面を描画します。起動音は内蔵の200ms PCMを
通常の音声出力とダイヤル・最大ゲインを通して再生し、再生完了後にSDを初期化します。
待ち時間には上限を設け、ゲームが別のサンプルレートを使う前に起動音を停止します。
正常起動時はスプラッシュを表示してから3秒以上経過するまでROMの読み込みを待ちます。
初期化が3秒を超えた場合は追加で待たず、SD初期化の失敗もすぐにエラー表示へ進みます。
スプラッシュ転送後は両フレームバッファを黒に戻し、初回のゲーム表示は全面転送します。
表示自体が初期化できない障害ではUSBシリアルに詳細を出します。

`engine --vm-opt size`が既定で、`--vm-opt speed`はVMコアの最適化比較用です。
speedは`mruby_config.rb`から`tools/build/vm_profile.rb`を通じて`picoruby-mruby`の
コンパイラだけを`-Os`から`-O2`へ切り替えます。VM、GC、基本コレクション等を含みます。
Game gem、描画C、別gemの拡張・Estalloc・スケジューラ、ホストコンパイラ、WASMの最適化は変更しません。
整数幅・ABI・gem構成・GC方式・LTO・浮動小数点の規則も同じです。

sizeのクロス出力は`build/mruby/`、speedは`build/mruby-vm-speed/`です。
各`pico-gaming/gaming-build.json`に設定・コンパイラ・依存版・構成ファイルのハッシュを記録します。
記録と現在の設定が異なる場合は、その生成済みクロスターゲットだけを作り直します。
別checkoutやホストコンパイラの既存ファイルは削除しません。CMakeはリンク先ライブラリの
記録からプロファイルを読み、起動時の`VM: profile=... scope=picoruby-mruby`へ反映します。
記録がない古いライブラリはworkflowから再ビルドします。Debugとのspeed併用は拒否します。
標準releaseの採用設定は実機比較までsizeを維持します。

## 共通部分

組み込み文字の`Game::Display.text_aligned`は共通gemのRuby実装で基準座標から
描画開始位置を求め、各バックエンドの`Game::Display.text`に渡します。

三角形はspansで各行の有効区間を走査します。幅16画素未満ならrowsへ戻します。
起動ログの`triangle=2`はこの標準方式を示します。旧方式はホストの回帰比較で使います。
常設の作業領域を増やさず、描画原点・画素中心・辺の包含・逆深度と比較規則・dirty登録を維持します。
Cは投影後の固定座標が±4096画素の範囲を超える場合、従来の行頭再計算と矩形走査へ戻します。
スタック上の一時値は増えるため、常設メモリ不変を最大スタック使用量不変とは扱いません。

WASMの同等経路は読込前の`window.GAME_3D_TRIANGLE_MODE`（0〜3、既定2）で検査します。
Game APIではありません。固定座標の絶対値が512×65536を超える場合、または逆深度の累積に
Numberの正確な整数範囲を保証できない場合は、従来の行頭再計算へ戻します。
RP2350の64bit整数とWASMのNumberの丸めを同一視せず、各バックエンドの旧版と比較します。

`mrbgems/picoruby-game-common/`は、実機とWASMの両方に組み込む共通gemです。共有する
gemの一覧は`tools/runtime_profile.rb`で管理します。

ゲームが使う共通の契約は次のとおりです。

- `Game::API_VERSION`
- `Game::Capabilities::*`
- `Game::Runtime`
- `Game::Input`、`Display`、`Assets`、`Sprite`、`Texture`、`Font`
- `Game::ThreeD`、`Audio`、`Save`、`Collision`、`Time`

`Sprite#draw_batch`は、`[x, y, frame, ...]`形式の整数配列を受け取り、実機ではC側、
WASMではJavaScript側で一括処理します。

`Game::ThreeD`は、実機ではSRAMまたはPSRAM上の深度バッファとフレームバッファへ、WASMではCanvasから
取得したフレームへ、同じワールド座標の三角形とwireframe edgeをソフトウェアラスタライズします。
ゲームから見える契約はカメラ、near/farクリッピング、深度比較、RGB565色、共有頂点を使うindexed meshと
wireframe edge描画です。

API 14の`Game::ThreeD::Model`は形状を登録時にコピーし、描画時には9値のインスタンス変換を
受け取ります。RP2350の実装は`mrbgems/picoruby-game/src/mruby/model.c`です。GC所有の
VMヒープ（PSRAM）にローカル頂点、索引、色、辺、ワールド頂点作業領域を1回で確保し、
描画時にはその領域と既存レンダラのカメラ空間作業領域を再利用します。モデル単位で最大256頂点、
1024三角形、2048辺、呼び出し単位で最大128体です。大きなモデルはゲーム側で分割します。
頂点のモデル変換はCの単精度で行い、三角関数は1体につき各軸で一度求めます。
三角形と線は既存のクリップ・カリング・深度・走査経路を使います。

WASMではアダプタが登録値と変換値をJSON文字列でJavaScriptへ渡します。上流ブリッジの
永続参照表へ配列を残さず、モデルの数値IDだけを`AssetLease`で保持します。JavaScriptは
Float32のローカル頂点とワールド頂点作業領域、Uint16の索引・色・辺を保持して再利用します。
既存レンダラ内のカメラ変換用オブジェクトと、毎フレームの変換JSON・解析配列は一時領域です。
モデルの形状を毎フレームRubyから送ることはありません。
`Assets.resident_bytes`には両環境でモデルの生データとワールド頂点作業領域を加算します。
カメラや解像度を変えても、以前の投影結果を保持モデルから流用しません。

描画バックエンドの共有投影キャッシュは保持モデルとは別の領域です。RP2350ではPSRAMに
256件の投影値と世代番号を確保し、indexed mesh／wireframeの呼び出しごとに世代を更新します。
番号が周回すると全エントリを無効化します。直接の単一三角形描画、クリップ生成点、float経路は
再利用しません。WASMは描画ごとに生成するカメラ空間頂点へ結果を付けます。
Modelで面と線の両方を描く場合は、既定ONの`GAME_3D_MODEL_SHARED`により、同じインスタンスの
面→線の間だけカメラ空間頂点と投影値を共有します。Cは内部の`game_3d_draw_model_geometry`を
使い、成功した固定小数点meshの作業領域と世代を線まで維持します。floatへのフォールバックは
従来の面・線の独立経路です。WASMは同じインスタンス内の準備結果を2つの私有描画関数へ渡し、
固定・floatのカメラ変換を共有します。別インスタンスと公開配列APIは準備をやり直します。
追加の常設領域や保持モデルのフィールドはなく、保持バイト予算も変わりません。
投影は両方とも裏面・不要な頂点を先に投影しない方式です。
投影キャッシュと線クリップは標準です。線クリップは元の線走査の位相と深度を保持して
画面外を飛ばします。Game APIは14のままです。

Core 1 presenter構成の`GAME_3D_DEPTH_SRAM`も既定ONです。Core 0専用の固定38400バイトを
内蔵SRAMに予約し、内部幅×高さが19200以下の深度に使います。160×120だけでなく320×60も
対象です。大きい解像度には従来の153600バイトのPSRAM領域を残し、成功した解像度設定時に
ポインタだけ切り替えます。解像度変更はフレーム中に拒否し、次の`begin_frame`で使用範囲を
ゼロクリアします。再確保やデータ移送はありません。PSRAM確保失敗時は従来どおり3D全体を
無効とし、小解像度だけ対応する状態にはしません。Core 1なしでは従来の全解像度SRAMを維持します。
WASMは従来の深度配列を使い、同じ解像度変更・フレーム終了の契約を検証します。
深度はCore 1が読むカラーのダブルバッファと別領域です。共有作業領域のため
`Assets.resident_bytes`には含みません。メモリ予算と比較手順は[性能メモ](performance-notes.md)を参照します。

共通APIの詳細は[`api-reference.md`](api-reference.md)を参照します。

## RP2350側

Pico SDKの`PICO_BOARD`で実機ターゲットを選びます。標準は
`pimoroni_pico_plus2_rp2350`、追加対応は`weact_studio_rp2350b_core`です。WeAct向けはSDKの
ボード定義からRP2350B、16MBフラッシュ、GP0のPSRAM CS1、8MB PSRAMを設定します。エンジンの
ディスプレイ、SD、入力、音声GPIOは両ボードで共通です。WeAct Core Boardには周辺機器が載って
いないため、[実機ガイド](hardware.md)の配線表に沿って外付けします。

`mrbgems/picoruby-game/`はRubyから呼び出すC拡張、`src/`と`include/`はハードウェア処理を
担当します。C拡張もmrubyのgemとしてコンパイルし、公開する名前をpresym生成に含めます。
CMake側とmruby側で`MRB_NO_BOXING`とconstrained profileを揃えます。
Core 0のCスタックは通常SRAM上端の16KiB（`0x2007c000`〜`0x20080000`）、
Core 1は物理SCRATCH_Xの4KiBを使います。SDKの論理SCRATCH_Y領域をCore 0用に再配置し、
通常RAMの上限も同じ境界まで縮めて、静的データ・ヒープ・Core 1との重なりを防ぎます。
PicoRuby 4.0.5のリリース構成ではVMの1関数だけで約3.2KiBを使うため、旧4KiB設定を維持しません。ゲームgemの
`allocator.c`は上流のEstallocだけを組み込み、VMヒープを8バイト境界で管理します。

PicoRuby 4.xで旧FatFs gemが削除されたため、SD用Cソースは最後の上流版を
`deps/picoruby-fatfs`へ独立して固定します。PicoRuby本体へ旧コードを戻さず、CMakeの
`FAT_ROOT`から既存のSDポートを参照します。

- TFT：ST7789V、SPI、DMA。SRAM上のダブルフレームバッファを
  Core 0/1間で交換するCore 1 presenterを使い、Core 1がTFT SPI0とDMAを
  単独所有する。Core 1はPSRAMへアクセスせず、ゲームのRuby・描画APIやWASM実装は変更
  しない。
- SDカード：FatFs、SPI
- メモリ：PSRAMの先頭4MiBはVMヒープ。残りは起動時バッファとROMを先に配置し、その後を
  アセット用の独立したEstallocヒープにする。64KiBのSRAMスプライトキャッシュも別の
  Estallocヒープとし、GCの解放後に空き領域を結合して再利用する。起動用領域とROMは移動しない。
- アセット：RubyのDataオブジェクトの解放コールバックから、画像・フォント・WAVと記述子を
  回収する。途中でロードに失敗しても、そのロードの割り当てを解放する。空き不足時はRuby GCと
  未使用の音声キャッシュ回収後に一度再試行する。`Audio.play`のキャッシュは最大8件。
  背景のRuby Stringは登録先モジュールが参照を保持し、`set_background(nil)`で解除する。
- 再生中のSound：所有するRubyオブジェクトが回収されても、IRQの参照がある間は解放を保留する。
  IRQは確保・解放せず、Core 0のフレーム処理・回収処理が音声データを解放する。
- 標準ライブラリ：ゲームロジックと3Dテスト用に`mruby-math`を含める。`picoruby-rng`の
  `rand`を実機とWASMで使い、実機はPico SDKの`pico_rand`を乱数源とする。
- 3D：最大320×240の16-bit深度バッファを確保し、設定した内部解像度で透視投影と三角形・wireframe edgeの
  ラスタライズを行う。ビューポートへの最近傍出力、裏面カリング、頂点変換・投影と内側ループの
  固定小数点化、indexed meshとwireframe edgeをRP2350/WASMで共通に実装する。Core 1 presenter構成では
  indexed mesh用作業領域にPSRAMを使う。深度は既定で19200画素以下をSRAM、それ以上をPSRAMへ配置する
- 音声：GP15のPWM（既定）またはMAX98357A用I2S、PCM WAV、BGM 1音とSE最大4音。DMA完了時は次の転送を開始してから
  空きバッファを補充する。再生状態の確認とボイス登録はCore 0の割り込み禁止区間で行い、
  音声終了割り込みとの競合を防ぐ。BGMは最大1 MiBをPSRAMへ全読み込みし、
  ループ時はフェードせず音源末尾から先頭へ戻る。SEの上限は128 KiB。
- 入力：GP2〜GP7、GP9、GP12、GP14、GP16（十字キー、A/B、L/R/START/SELECT）。
  Core 0の1msタイマーでボタンごとに5msのデバウンスを行い、フレーム境界で確定状態を
  取得する。タイマーが確保できない場合はフレーム単位の読み取りへ戻す。

実機はSDカードの`game.mrb`を起動し、`assets/`から読み込みます。

### I2S出力の実装

`engine --audio-output i2s`は`GAME_AUDIO_I2S=ON`を渡し、既定PWMと別のUF2へ分離します。
`src/game_audio_i2s.pio`をSDKのpioasmで生成し、PIO0の空きSMを1つ、8命令、DMAを2チャネル使います。
PIO／DMAを確保できない場合は初期化ログへ出し、再生要求は失敗します。PWMへの暗黙切替は行いません。
GP26=BCLK、GP27=WS、GP28=DINを既定とし、DATAはGP17も選べます。BCLK/WSとDATAの重複を拒否します。

ミキシングはPWMと共通の`audio_mix_sample`で、元WAVのサンプル位置・音量・fade・BGM 1/2と各SE 1/8の固定ゲイン加算を維持します。
unsigned 8-bit PCMは、中心値の設定定数も明示的に`int`へ変換してから128を引きます。
音量・fadeの乗除算をsignedで行い、負の半波を保ったまま加算とクランプへ渡します。
中心値`128u`のまま引くと負値がunsignedへ変換されるため、符号変換の位置も契約として検査します。
この修正を含むUF2は、起動時のPWM／I2SのAUDIO行に`pcm=signed`を付けます。
`include/game_audio_i2s.h`はそのsigned 8-bit相当値を16-bitへ拡張し、位相をバッファ間で保持して48kHzへ
線形補間します。48kHzを超える元音源も再生時間を維持して変換しますが、専用の帯域制限フィルタは含みません。
補間は差分の符号と絶対値を分けた32-bit整数演算です。16-bit PCMの最大差65535と
位相47999の積はuint32_tへ収まり、従来のsigned 64-bit除算と同じゼロ方向への丸めになります。
起動時の`math=32`で確認できます。ホスト上の一致は実機での音質改善を意味しません。
左右へ同じsigned 16-bit値を詰め、32-bit DMA→PIO FIFOからMSB-first・WSの1bit遅延で送ります。
PIOは1ステレオフレーム64サイクル、BCLKは32倍です。WAVの8-bit形式と既存の再生APIを維持します。

I2Sは512フレーム×2の32-bitバッファ（4096B）で、PWMの2048サンプル×2（4096B）と同じ容量です。
2つのDMAを相互にチェーンし、転送完了時にハードウェアが次のバッファを開始します。
IRQは空いたバッファを補充します。各2KiBのバッファは2048バイト境界に置き、DMAのread ringで
バッファ内に折り返します。補充が遅れても割り当て外を読みません。既に再読込中なら補充を避け、
遅延を記録します。補充中に期限を超えた場合も記録しますが、その場合の音の連続性は保証しません。
EOFでは空き側の転送数を0にして再読込を止め、最後の転送完了で両DMAのチェーンを解除・停止します。
明示的な停止でもチェーンを両方解除してからabortし、相互に再起動しないようにします。
BGM 1音・SE 4音・同一入力レート制限は共通です。
最終バッファの再生中に新しい音源が登録された場合、終了扱いにせず空きバッファを補充して
DMAを再開します。チェーン停止後の再開では一時的な無音やPIO停止が発生する可能性があります。
再生完了／全停止時はDMA割り込みを解除し、PIOを無効化・FIFOをクリアしてデータ／時計をLOWに戻します。
次の再生で位相とPIOのワード境界を初期化します。個別Sound停止では他の音源を継続します。
実機での起動、停止時のポップ、IRQ補充期限と長時間併用は確認が必要です。
再生停止時／次の再生開始前に`AUDIO: I2S stats`を出し、IRQ内ではログを出しません。
転送開始前はFIFOに最初のワードが届くのを待ち、その後でPIOの時計を開始します。
各再生開始時にPCM診断を初期化し、全体音量を適用した最初の4096モノラルサンプルを
little-endian signed 16-bitの2バイトとしてFNV-1aへ積算します。`pcm_frames`、`pcm_fnv1a`、
隣接サンプルの最大差`pcm_max_step`をstatsへ追加します。短い音源では末尾の無音も含み、
途中停止では4096未満になります。4096到達後は積算を止めます。自然終了後も結果を保持し、
停止／次の再生開始時に一度だけ表示・初期化します。DMAへ渡す前の生成波形の診断であり、
配線上の波形やアンプの受信結果は測定していません。
WASMは従来どおりWeb Audioを使い、物理I2Sの設定をRuby／JavaScriptへ公開しません。

### ADCによる全体音量

`engine --volume-knob`は`GAME_AUDIO_VOLUME_KNOB=ON`と`hardware_adc`を有効にします。
`src/game_audio_dial.c`がADC2/GP42を専有し、入力用1msタイマー内で20msごとに4回平均を
取ります。初期読み取りはタイマー開始前で、タイマー確保失敗時だけフレーム更新時に読みます。
ゲームからの照会はキャッシュを読むため、IRQと前景からADCを同時操作しません。
音量はQ8の1/4 IIR平滑化と両端のデッドゾーンを通し、再生中も更新します。
128以下を無音、3800以上を最大とし、中間を0〜255へ線形変換します。ADC生値は変更しません。

Pico Plus 2ではヘッダGP28のデジタル側を無効にし、ADC側GP42を使用します。
I2Sとの併用時はDINを既定でGP17へ移します。Pico PlusはGP26/27/17を必須とし、
WeActだけは明示的な`--i2s-data 28`も許可します。WeActのGP28はADC GP42と独立しています。
GPIOの変更はビルド設定に閉じ、ゲームとWASMには同じAudio APIを提供します。
通常のUF2はADCに触れず、全体ゲイン255です。API 15の`AUDIO_DIAL`と3つの読み取りAPIで
対応状態を公開します。WASMでは共有操作パネルのスライダーを仮想ADCとし、各音源の後段に
1個のマスターGainNodeを置きます。

`GAME_AUDIO_MAX_GAIN`はビルド時の0〜100%で、PWM・I2Sのミックスおよびダイヤル適用後に
符号付きPCMへ乗算します。既定100%は従来の出力を維持し、`master_volume`の値は変えません。
出力設定は実機固有で、WASMには適用しません。起動時に`AUDIO: max_gain=...%`を出します。

PWMは8-bit PCMのまま中心128を保って全体ゲインを適用します。I2Sは48kHzへ補間した後の
signed 16-bit値へ適用して、低音量でも8-bitへ再量子化しません。ゲインはバッファごとに
一度取得します。停止・再初期化は物理／仮想ダイヤル位置をリセットしません。

## WASM側

`emulator/game_adapter.rb`は同じRuby APIをCanvas、JavaScript、HTTPで配信するアセット、
ブラウザの永続ストレージへ接続します。アダプタの定義後に`game`を`$LOADED_FEATURES`へ
登録し、ゲームの`require 'game'`を満たします。`emulator/browser-bridge.js`と`emulator/shell.rb`は`local-games/`の
ディレクトリ一覧から`main.rb`を持つゲームとアセットを検出し、通常のエミュレータ入口へ
動的に接続します。

- 画面：Canvas
- 3D：Canvasの現在画像を基準にした16-bit深度バッファ付きソフトウェアラスタライズ。内部解像度、
  ビューポート、裏面カリング、固定小数点の頂点処理・内側ループ、indexed mesh、wireframe edgeは
  実機側と同じ契約
- 入力：キーボード（Q/E＝L/R、P/O＝START/SELECT）と画面ボタン
- アセット：ゲームディレクトリの`.raw`、`.pbf`、`.wav`をHTTPで自動検出して読み込み
- 音声：Web Audio API
- セーブ：ブラウザの永続ストレージ

通常の`emulator/index.html`ではFunicularの`emulator/shell.rb`がゲームとアセットを選び、
`emulator/browser-bridge.js`が取得して起動します。
契約テストやサンプルなどの固定ページでは、`emulator/browser-bridge.js`のページ設定で
Rubyソースとアセットを指定します。

### 3DとCanvasの同期

WASMの3D描画は1枚のImageDataを更新し、実際に画素が変わったときだけ未反映として記録します。
連続する3D呼び出しの途中ではCanvasへ転送せず、2D描画の直前または`Display.present`で
まとめて反映します。2D描画後は作業画像を無効化し、次の3D呼び出しで最新のCanvasを取得します。
これにより`3D → HUD → 3D`でもHUDが古い作業画像で消えません。深度バッファは2D描画で消去しません。

`clear`と背景の全面復元は未反映画像を破棄して画面全体を置き換えます。同じ背景を再指定する
操作は従来どおり何も変更しません。`ThreeD.begin_frame`は未反映画像を確定してから深度を
消去し、ゲーム初期化の同期処理でも未反映画像を確定します。`Display.present`はC・WASMの
両方で3Dフレームを終了し、次の`ThreeD.begin_frame`より前に解像度・ビューポートを変更できます。空バッチ、全カリング、深度不合格
だけのバッチはCanvasへ追加転送しません。2Dだけのゲームでは3D用の取得・反映は発生しません。

## アセット形式

PBFフォントはロード時に全サイズ・全グリフの範囲を検証し、不変の内部データとして保持します。
RP2350ではPBF内のサイズ表・グリフレコードをそのまま再利用し、文字列ごとの全体再検証や
追加の索引確保を行いません。グリフの可視範囲を先に求め、不透明画素はRGB565へ直接書きます。

WASMはサイズ・グリフをロード時に解析します。2値alphaのフォントは色別の文字画像を、
中間alphaを含むフォントは描画区間を再利用します。半透明の画素は従来の1画素合成を保ちます。
キャッシュは全フォント合計256件・予算1MiBのLRUです。予算は画像のRGBAバイト数、または
区間1件40バイトで計算し、ブラウザ内部の管理領域は含みません。大きすぎる文字は可視画素だけを
直接描きます。FontのGC時には該当分を、`Assets.collect`時には全キャッシュを破棄します。
改行などの制御文字はアダプタ内でJSON文字列に包み、上流の複数引数ブリッジを安全に通します。

WASMのSprite・Texture・Font・Sound・ThreeD::Modelは数値IDで管理し、共通gemの`Game::AssetLease`がRuby GC時に
JavaScriptのハンドルを解放します。上流JSブリッジの参照表へデータ本体を登録しないための内部型です。
再生中の音声だけは終了まで保持します。仮想SDとして事前ロードする元データと、描画・再生用の
管理ハンドルは別管理です。`resident_bytes`は後者の生データ量を表し、ブラウザ全体の使用量ではありません。
WASM配布時は生成物・`emulator.js`・`game_adapter.rb`のSHA-256を`version.json`へ記録し、
読み込みURLのキャッシュキーに使います。PicoRubyの上流コミットが同じでも、ゲーム用C拡張や
ブラウザの描画・受け渡し処理を変更したビルドを区別します。

実機で画像をデコードしないため、開発時に変換します。

| 元データ | 実行時データ |
| --- | --- |
| PNG | ビッグエンディアンRGB565の`.raw` |
| TTF / OTF | アルファマップの`.pbf` |
| WAV | PCM WAVをそのまま使用 |
| その他 | そのままコピー |

変換は`ruby tools/build/workflow.rb game GAME_DIR --convert-assets`で行います。

## APIを追加するときの境界

- ゲームに公開する型と名前は`Game` APIにする。
- Cのポインタ、GPIO、Canvasオブジェクトは公開しない。
- 実機とWASMの両方に同じ引数、戻り値、エラー条件を実装する。
- 実行先によって使えない機能は能力ビットで表す。
- 共通gemは`runtime_profile.rb`へ追加し、ターゲット固有の処理は各バックエンドに置く。

API変更の手順は[`extension-guide.md`](extension-guide.md)にあります。

### WeActの電池警告

任意の`--battery-warning`ではGP40/ADC0を入力タイマーで20msごとに測定し、
音量ダイヤルのADC2との切り替えを同じタイマー内で直列化します。2.2V以下または2.4V以上が
約3秒続くまで状態を変えません。GP24のLEDは通常点灯、低電圧時は0.5秒ごとに切り替えます。
入力タイマーが利用できない場合はフレーム更新時に測定・点滅します。ゲームAPIやWASMの
動作は変えません。配線と測定条件は[実機ガイド](hardware.md#電池残量のled警告weact単3アルカリ2本)を参照します。
